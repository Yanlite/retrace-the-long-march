## 添加一条事件

在对应文件的数组里添加一个对象，注意前后对象间的逗号。JSON 不允许注释、末尾多余逗号或单引号。以下是格式示例，不需要照抄成实际史实：

~~~json
{
  "id": "example-tucheng-report",
  "mode": "auto",
  "date": "1935-01-28",
  "dateLabel": "1月28日 · 土城战斗",
  "routeIndex": 24.06,
  "side": "blue",
  "place": "土城以东",
  "headline": "川军从东面逼近土城",
  "text": "川军从习水方向向土城逼近，威胁红军侧后。",
  "chapterId": "chishui",
  "locations": ["土城", "青杠坡", "习水"],
  "focus": {
    "id": "tucheng-eastern-approach",
    "places": ["土城", "青杠坡", "习水"],
    "maxZoom": 10,
    "regional": true
  },
  "part": 2,
  "source": "https://www.bilibili.com/video/BV1fV411H7VK/?p=2&t=405",
  "sourceLabel": "视频讲义参考"
}
~~~

| 字段 | 用法 |
| --- | --- |
| id | 唯一且稳定。引用、互动及进度会使用它，修改旧记录时尽量不改 id |
| mode | auto 自动播放；archive 仅档案 |
| date | YYYY-MM-DD，用于排序关联与月份动画；不确切的日期应保留宽泛的 dateLabel，勿伪造日级考证 |
| dateLabel | 弹窗显示的时间说明，可省略 |
| routeIndex | 路线控制点索引，可带小数；不是公里数，也不是经纬度。应与前后事件的历史顺序一致 |
| side | red 红军；blue 国民党军。决定弹窗配色，不等于宣称该地点已被占领 |
| place | 事件所在地点或区域文字 |
| headline / text | 标题 / 正文；context 可选，仅用于必要的补充，避免重复 |
| chapterId | 归入哪个大节点档案，例如 chishui。仿照同段现有记录填写 |
| locations | 要在地图上点名的地点，名称须已登记；不要因为写了正文就假设一定会自动识别 |
| focus.id | 同一连贯视野使用相同 id；不要让相距很远的地域共用一个视野 id |
| focus.places | 镜头可参考的已有地点 |
| focus.maxZoom | 最大放大级别，数值越大越近；实际还会缩小以容纳全部指向地点 |
| focus.regional | true：手机也保留该事件的地域参照；适合河段、行军走廊、草地等 |
| focus.points | 可选，额外取景坐标，顺序为 [纬度, 经度]，不自动画地点标记 |
| part / source / sourceLabel | 对应视频选集、来源链接及显示名称 |

运行 node scripts/list-events.mjs 可查看全部事件的 routeIndex、虚拟公里数和播放状态。安排新事件时，先对照同路段的几个索引，不要靠猜绝对公里数。

## 地点与部署

已有地点登记在 lib/event-places.mjs 的 places 及 lib/chishui-geography.mjs。新地点要先有可信的坐标依据，再添加到字典，并在 locations 中引用。

一次性示意位置可使用 anchors 替代 locations：

~~~json
"anchors": [
  {"name": "川军追击方向（示意）", "point": [28.30, 106.11]},
  {"name": "土城", "point": [28.31, 105.99]}
]
~~~

anchors 优先于 locations，不要同时填写两套矛盾的位置。anchor（单数）只用于明确弹窗的主指向点，可省略。方位与兵力部署只能标为有依据的示意，不把城市坐标当作精确部队位置。

正文里出现影响判断的陌生地点或部署，应在地图上对应呈现；无法可靠表现时应调整文案。河流显示区段在 lib/map-context.mjs，河道在 public/rivers.json。不要把河流名作为普通城市匹配，也不要拿一个虚构坐标冒充整条河道。

持续占领状态在 lib/place-control.mjs；土城川军方向图层在 components/march-map.tsx。写新事件本身不会自动生成新的占领圈或部队箭头，需另外维护有依据的状态区段。

## 互动与揭示顺序

在 data/interactions.json 中以事件 id 为键增加配置。可以复制现有条目；方向选择参考 chishui-old-plan，行走参考 chishui-silence，分批战报参考 chishui-estimate。

preview 的 headline、text 是作答前显示的局势，事件自身的结果标题和正文在作答后才揭示。先给出决策所需的地形、敌情和物资信息，不能把答案提前写在屏幕上，也不能事后才补关键条件。

walk / reports 使用现实有效 GPS 距离 walkMeters；进度条不能完成这类任务。不要求用户加速、折返或走陌生道路，必须保留略过。

## 路段有效期与阅读时间

通常自动根据下一事件和最大路段范围计算。需要特殊有效区段时可增加：

~~~json
"until": {"event": "chishui-crossing", "km": 80}
~~~

表示有效到该事件触发位置之后80虚拟公里；不是停留80秒。超过区段，未完成的互动也会跳过，避免积压到下一地域。

阅读、互动反馈和入场时间在 lib/timeline.mjs 的 PLAYBACK，单位毫秒。阅读从镜头与消息可见后计时，没有独立的镜头冷却时间。

修改后保存，开发预览会更新。回退到事件之前再向前经过，才能重新触发；刷新页面不会补播已走过的事件。提交前可运行 npm run check 和 npm run build。
